# Задание 4. Проектирование сервиса ОСАГО и паттернов отказоустойчивости

## 1. Бизнес-контекст и требования

* **Новый продукт**: Оформление ОСАГО онлайн.
* **Пользовательский сценарий**: Клиент заполняет данные об авто &rarr; система параллельно опрашивает 10 страховых компаний (СК) &rarr; **предложения от каждой СК появляются на экране мгновенно по мере поступления** (без ожидания остальных).
* **Ограничения**:
  * Максимальное время ожидания ответа от СК — **60 секунд**.
  * Однотипный REST API у всех СК: `POST /applications` (создание заявки) и `GET /applications/{id}/proposals` (опрос статуса).
  * Пиковая нагрузка: до **2 500 одновременных пользователей**, оформляющих заявку.
  * Сервисы развернуты в **нескольких экземплярах (Multi-instance)**.

---

## 2. Архитектурные решения

### 2.1. Сервис `osago-aggregator` и хранилище данных
* **Нужно ли собственное хранилище?** **Да, обязательно (`osago-aggregator-db` — PostgreSQL / Redis)**.
  * *Обоснование*: Так как сервис задеплоен в нескольких репликах, хранилище необходимо для координации опроса СК: сохранение сопоставления внутренних `application_id` с внешними ID заявок в СК, фиксация статусов опроса (`PENDING`, `READY`, `FAILED`, `TIMEOUT`), дедупликация и предотвращение повторных вызовов разными подами агрегатора.

### 2.2. Интеграция `core-app` &harr; `osago-aggregator`
* **Средство интеграции**: **Apache Kafka** (асинхронная событийно-ориентированная модель).
  1. `core-app` сохраняет заявку в `core-db` и через **Transactional Outbox** публикует событие в топик **`osago.applications`**.
  2. Реплики `osago-aggregator` вычитывают заявку, распределяют запросы в 10 СК и запускают параллельный поллинг.
  3. По мере готовности котировки от конкретной СК `osago-aggregator` сразу публикует событие в топик **`osago.proposals`** (ключ `application_id`).
  4. `core-app` слушает топик `osago.proposals` и незамедлительно транслирует котировку в браузер клиента.

### 2.3. Интеграция веб-приложения и `core-app`
* **Проблема REST-поллинга**: При 2 500 клиентах опрос каждые 1–2 секунды создаст паразитную нагрузку в 1 250–2 500 RPS на `core-app` и БД с задержкой появления карточек.
* **Выбранное средство интеграции**: **Server-Sent Events (SSE)** поверх HTTP/2.
  1. `POST /api/v1/osago/applications` (REST): отправка формы, валидация, получение `application_id`.
  2. `GET /api/v1/osago/applications/{id}/proposals/stream` (SSE): открытие однонаправленного потокового канала от сервера к браузеру. Как только предложение попадает в `core-app` из Kafka, оно пушится в открытый SSE-поток. По истечении 60 секунд сервер отправляет событие закрытия стрима.

### 2.4. Учет нескольких экземпляров сервисов (Multi-instance)
* Клиент устанавливает SSE-соединение с конкретным подом `core-app`.
* Поскольку событие из Kafka может попасть на любой под `core-app`, внутри кластера используется внутренняя шина рассылки (Kafka Consumer Group с Fan-out / Redis PubSub), направляющая предложение именно на тот инстанс, где открыта SSE-сессия пользователя.

### 2.5. Архитектурная оптимизация: вынос Push Gateway / SSE Proxy
* **Трейдофф текущего решения**: Удержание 2 500+ долгоживущих сокетов непосредственно на бизнес-монолите `core-app` создает накладные расходы при rolling-update подов (массовые обрывы и шквал реконнектов *Thundering Herd*), а также усложняет маршрутизацию событий между репликами.
* **Рекомендуемая эволюция (TO-BE Evolution)**:
  Выделение легковесного специализированного шлюза **Push Gateway / API Gateway** (на Netty, Go или Node.js):
  1. Веб-клиент держит постоянное SSE/WS-соединение со шлюзом `Push Gateway`.
  2. `Push Gateway` подписывается напрямую на Kafka-топик `osago.proposals`.
  3. `core-app` полностью освобождается от управления сетевыми сокетами и занимается только бизнес-логикой и транзакциями.
### 2.6. Дополнительные инженерные решения
* **Паттерн Bulkhead (изоляция пулов HTTP)**: В `osago-aggregator` пул соединений разделяется на 10 независимых изолированных пулов (по одному на каждую страховую компанию). Если одна СК отвечает медленно (до 60 секунд), она утилизирует только свой лимит соединений, не замедляя отправку и опрос предложений по остальным 9 компаниям.
* **TTL и автоочистка в `osago-aggregator-db`**: Состояния заявок и промежуточные расчеты актуальны только во время пользовательской сессии. В БД настраивается короткий TTL (2–3 минуты через Redis `EXPIRE` или партиционирование PostgreSQL), что предотвращает разрастание базы данных при пиковой нагрузке в 2 500 одновременных заявок.

## 3. Применение паттернов отказоустойчивости

| Паттерн | Точка применения | Назначение и параметры |
|---|---|---|
| **Rate Limiter (на входе)** | Входящие запросы от веб-приложения к `core-app` | Защита от ботов и спама: ограничение частоты на пользователя (например, не более 5 заявок в минуту с одного IP/аккаунта) и общий шлюзовой лимит с запасом (headroom) от DDoS. Пиковые 2 500 одновременных пользователей создают реальный поток порядка 50–100 RPS на оформление, поэтому лимит не должен отсекать легитимных клиентов. |
| **Rate Limiter (для партнеров)** | Исходящие запросы от `osago-aggregator` к каждой страховой компании | Соблюдение партнерских квот внешних API (например, не более 30–50 RPS на конкретную страховую компанию), чтобы наши параллельные опросы не привели к бану со стороны партнеров. |
| **Timeout (60 секунд)** | Запросы `osago-aggregator` в сторону внешних страховых компаний | Бизнес-дедлайн 60 секунд на ожидание предложения. Если страховая компания не успела ответить за минуту, заявка по ней помечается просроченной, а пользователь видит результаты от ответивших компаний. |
| **Retry** | Опрос статуса котировок в `osago-aggregator` | Периодический опрос решений с экспоненциальной паузой (Exponential Backoff: 2с &rarr; 4с &rarr; 8с) и безопасный повтор при сетевых сбоях (502/503/504). |
| **Circuit Breaker** | Интеграционный HTTP-клиент каждой страховой компании | Изоляция сбойных партнеров: если конкретная страховая компания падает серией 5xx или таймаутов, цепь размыкается (Open). Сервис временно прекращает слать в нее запросы и мгновенно возвращает статус недоступности. |
| **Bulkhead** | Пул HTTP-соединений сервиса `osago-aggregator` | Изоляция пулов соединений по каждой компании: зависание одной страховой компании на 60 секунд расходует только ее квоту потоков и не замедляет опрос остальных девяти партнеров. |

### Что добавлено на схеме:
1. Контейнер **`osago-aggregator`** (Kotlin, Spring Boot) и его база данных **`osago-aggregator-db`** (PostgreSQL / Redis).
2. Новая стрелка интеграции **`Web ➔ core-app` [SSE / HTTP/2]** для мгновенной потоковой передачи предложений клиенту.
3. Топики Kafka: **`osago.applications`** (передача заявок в агрегатор) и **`osago.proposals`** (мгновенный стриминг котировок от СК).
4. Связи `osago-aggregator ➔ 10 СК` по REST API с эндпоинтами создания заявки и опроса предложений.
5. Иконки паттернов отказоустойчивости (**Rate Limiter, Timeout, Retry, Circuit Breaker**) согласно библиотеке.
6. Выносная архитектурная заметка **«💡 Архитектурная оптимизация (TO-BE Evolution)»** о целесообразности будущего выноса **Push Gateway / API Gateway** для терминации SSE-соединений.
